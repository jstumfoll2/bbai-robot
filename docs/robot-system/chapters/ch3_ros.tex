\section{NETWORK AND MASTER}

ROS~1 is used throughout: Melodic on the board (built from source into
\texttt{/opt/ros/melodic}) and Noetic on the laptop. The two are compatible on
the wire for every message type used here. The board runs the ROS master, so
the board must be brought up first. Both machines set
\begin{lstlisting}
ROS_MASTER_URI=http://192.168.3.120:11311
ROS_IP=<own address>       # 192.168.3.120 on the board, 192.168.3.147 on the laptop
\end{lstlisting}
\texttt{ROS\_IP} matters because ROS nodes advertise their own address to
the master; without it the laptop would advertise a hostname the board cannot
resolve. On the laptop the variables are set by
\file{laptop/bbai\_slam/env.sh}.

\section{COORDINATE FRAMES}
\label{sec:frames}

Frames follow ROS REP~103 and REP~105 \cite{rep103,rep105}: right-handed,
$x$ forward, $y$ left, $z$ up on the body, and east-north-up (ENU) for world
frames, with yaw $\psi$ measured counter-clockwise from the world $x$ axis.
REP~105 defines three world-fixed frames with different guarantees:
\begin{description}
\item[\frm{odom}] continuous (no jumps) but drifts without bound. Published by
  \texttt{bbai\_base} from wheel odometry and the gyroscope.
\item[\frm{map}] does not drift, but may jump when a correction arrives.
  Published by SLAM as the transform \frm{map}$\to$\frm{odom}.
\item[\frm{earth}/UTM] the GPS frame, related to \frm{map} by the navsat
  transform (\S\ref{sec:navsat}).
\end{description}

The three static transforms in \file{robot.launch} have zero horizontal offset
and zero rotation. They were entered as placeholders and have not been
measured. The lidar's yaw in particular must match how the A1 is physically
mounted, which matters for SLAM (\S\ref{sec:slamdiag}).

Each transform in the tree must have exactly one publisher. In particular,
only one node may publish \frm{odom}$\to$\frm{base\_link}: either
\texttt{bbai\_base} (\texttt{publish\_tf: true}, the current setting) or an
EKF, never both.

\section{BRINGUP SEQUENCE}

\begin{enumerate}
\item Board: \texttt{roslaunch bbai\_base robot.launch}. This starts the
  master, \texttt{rplidar\_ros}, \texttt{bbai\_base} (which measures the gyro
  bias for \SI{2}{s}, so the robot must be still), \texttt{gps\_node}, and the
  three static transforms. Arguments \texttt{lidar:=false} and
  \texttt{gps:=false} leave those devices out. \texttt{bbai\_base} is
  respawned automatically \SI{5}{s} after it exits.
\item Board: \texttt{roslaunch bbai\_teleop teleop.launch}.
\item Laptop: \texttt{\textasciitilde/bbai\_slam/start\_slam.sh [gmapping|hector|lidar\_only]}
  (gmapping by default), which also opens RViz.
\item Laptop, optional: \texttt{roslaunch \textasciitilde/bbai\_slam/gps\_fusion.launch}.
\item Board, optional: \texttt{roslaunch bbai\_chase chase.launch} (dry run
  unless \texttt{dry\_run:=false}).
\end{enumerate}
The full command list is \file{docs/COMMANDS.md}.

\section{BASE NODE}

\texttt{base\_node.py} runs a fixed-rate loop at \SI{30}{Hz}. Each cycle it
reads the IMU and the four encoders, integrates the pose
(Chapter~\ref{ch:kinematics}), publishes \topic{/odom}, the
\frm{odom}$\to$\frm{base\_link} transform, \topic{/imu/data\_raw},
\topic{/imu/mag} and \topic{/wheel\_ticks}, and enforces the command timeout:
if no \topic{/cmd\_vel} message has arrived for \SI{0.5}{s}, all motors are
set to zero. Motors are also zeroed when the node exits.

With \texttt{mag\_heading: true} it also publishes \topic{/imu/data}: the
same rates and accelerations as \topic{/imu/data\_raw} plus an orientation
whose yaw comes from the calibrated magnetometer (\S\ref{sec:mag}). While the
robot is parked it applies a zero-velocity update to the heading and the gyro
bias (\S\ref{sec:zupt}).

\influx{The compass output, the zero-velocity update and
\texttt{mag\_calibrate.py} are on branch \texttt{slam-estimator-updates}; the
version on \texttt{main} has neither.}

\section{PS4 TELEOP}

\texttt{ps4\_teleop.py} reads the Linux joystick API directly
(\texttt{/dev/input/js*}, 8-byte events of time, value, type and number) and
looks the device up by name (\texttt{Wireless Controller}), skipping the
controller's separate motion-sensor device. It publishes \topic{/joy} and,
only while the deadman button is held, \topic{/cmd\_vel}. Publishing runs as a
\SI{20}{Hz} heartbeat that speeds up to at most \SI{100}{Hz} while the sticks
move, and all queued events are drained on each read so the commands never
lag behind a backlog.

\begin{table}[htbp]
\centering
\caption{PS4 controller mapping (\texttt{hid-sony}, kernel 4.14)}
\label{tab:ps4}
\small
\begin{tabular}{lll}
\toprule
Input & Index & Effect \\
\midrule
L1 (hold) & button 4 & Deadman. Nothing moves unless held; release sends one zero Twist \\
Left stick vertical & axis 1 & \texttt{linear.x}, \SI{0.3}{m/s} full scale (turbo \SI{0.7}{m/s}) \\
Right stick horizontal & axis 3 & \texttt{angular.z} (curve below) \\
R1 (with L1) & button 5 & Turbo scaling \\
R2 (L1 released) & button 7 & Arms the chase node \\
\bottomrule
\end{tabular}
\end{table}

The stick values are $a\in[-1,1]$ after dividing by \num{32767}, with a dead
zone $\abs{a}<0.08$ mapped to zero. Stick ``up'' is negative on the joystick
API, so both axes are negated. In the repository version the command is
linear in the stick,
\begin{equation}\label{eq:teleop}
v = -k_v\,a_1,\qquad \omega = -k_\omega\,a_3,
\end{equation}
with $(k_v,k_\omega)=(0.3,1.5)$ normally and $(0.7,8.0)$ in turbo.

\influx{On 2 October 2026 the turn axis was changed to a curve because
\SI{1.5}{rad/s} at full stick could not overcome skid-steer friction
(\S\ref{sec:skidturn}). The installed version gives about
\SI{1.5}{rad/s} at half stick, \SI{6}{rad/s} at full stick and
\SI{10}{rad/s} at full stick in turbo. It is installed on the board but not yet
in the repository.}

\section{CHASE NODE}
\label{sec:chase}

Chapter~\ref{ch:chase} covers the chase behaviour in full; this section
summarizes the node.


\texttt{chase\_node.py} runs a MobileNet-SSD spatial detection network on the
OAK-D-Lite: the $300\times300$ RGB preview feeds the network on the camera's
VPU, and the stereo depth (aligned to RGB) gives each detection a 3-D position
$(x,z)$ in the camera frame, $x$ to the right and $z$ forward. The node keeps
the most confident detection whose label is in \texttt{targets} and computes a
bearing and range,
\begin{equation}
\beta = \atantwo(x,z),\qquad \rho=\sqrt{x^2+z^2},
\end{equation}
falling back to $\beta=(c_x-\tfrac12)\,\mathrm{HFOV}$ from the box centre
$c_x\in[0,1]$ when the box has no valid depth. Both are smoothed with an
exponential moving average of weight $a=0.5$. After at least 3 consecutive
detections the command is
\begin{align}
\omega &= \begin{cases}
  \sat_{\omega_{\max}}\!\left(-k_\beta\,\beta\right) & \abs{\beta}>\beta_{\mathrm{db}}\\
  0 & \text{otherwise}\end{cases}\\
v &= \sat_{[0,v_{\max}]}\!\bigl(k_\rho(\rho-\rho_f)\bigr)\cdot
     \sat_{[0,1]}\!\left(1-\frac{\abs{\beta}}{\beta_{\mathrm{full}}}\right),
     \qquad \rho>\rho_{\mathrm{stop}},
\end{align}
with $k_\beta=2.5$, $\omega_{\max}=\SI{2}{rad/s}$,
$\beta_{\mathrm{db}}=\SI{5}{\degree}$, $k_\rho=0.4$, $v_{\max}=\SI{0.2}{m/s}$,
follow distance $\rho_f=\SI{0.9}{m}$, $\beta_{\mathrm{full}}=\SI{25}{\degree}$
and stop distance $\rho_{\mathrm{stop}}=\SI{0.5}{m}$. The second factor of $v$
slows the robot while it is still turning toward the target. The robot never
reverses.

\paragraph{Command arbitration.} Both teleop and chase publish
\topic{/cmd\_vel}, and \texttt{bbai\_base} applies whichever arrives last.
Conflicts are avoided by the buttons: chase only publishes while R2 is held
and L1 is not, and teleop only publishes while L1 is held. Chase also stops
if \topic{/joy} goes quiet for \SI{0.5}{s} or the target is lost for
\SI{0.5}{s}. In the default dry-run mode chase never publishes
\topic{/cmd\_vel} at all, only \topic{/chase/cmd\_vel\_preview}.
